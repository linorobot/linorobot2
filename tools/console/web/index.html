Robot Configuration Profile (Single Source of Truth)

Import or export your complete robot profile via robot_config.yaml. Holds robot kinematics, LiDAR, depth camera, micro-ROS agent, EKF sensor fusion, and Nav2 navigation stack in one single file. Microcontroller firmware, pinouts, and flashing are managed in linorobot2_hardware; simply import your generated custom_config.h or robot_config.yaml below.

Install mode

Docker/Podman need no ROS install on this machine at all -- linorobot2's own docker/Dockerfile builds everything (including sensor drivers) inside the image; the console drives it from its own compose stack at tools/console/docker/. Useful on unsupported OS versions, or when you'd rather not touch the host. Native builds directly on this machine instead.

1. Base install

Clones linorobot2 (branch = detected $ROS_DISTRO) into the workspace, skips the Gazebo package, then rosdep install + colcon build. No setup script is invoked.

1. Build image

Writes tools/console/docker/.env + devices.generated.yaml (the base serial + lidar device mappings) into the console's own compose dir -- the repo's docker/ is never written -- then clones linorobot2 (if needed) and runs docker compose --env-file .env -f docker-compose.yaml -f devices.generated.yaml build. Sensor drivers install inside the image via linorobot2's own install.bash (the documented Docker build path, not run on this host).

2. Host udev rules

The image already contains the sensor drivers -- this only creates the persistent /dev/<sensor> symlink on the host, using Console's own native udev-rule commands (same as the native Laser/Depth sensor install cards above), not install.bash.

3. Run a service

Runs in the foreground through the same console pane as everything else in Console -- Stop sends the container(s) a normal compose stop signal. Start kasmvnc alongside bringup/slam/etc. (in a second Console tab, since each occupies the one exec slot) for GUI output from any of them.

Active parameters configured in ~/.config/linorobot2/robot_config.yaml (the single file of truth). Passed directly to our own launchers without environment files or .bashrc dependencies.

Robot bringup

bringup.launch.py starts its own micro-ROS agent internally (base_serial_port/transport/port below) -- Console does not launch a separate agent alongside it, since two agents on the same port would just fight each other. The manual agent controls in Settings are for other uses only (e.g. testing agent connectivity on its own).

These select the sensor model via LINOROBOT2_LASER_SENSOR/LINOROBOT2_DEPTH_SENSOR, using whatever connection details are hardcoded in linorobot2_bringup's own launch files (e.g. YDLIDAR/RPLIDAR already use persistent /dev/ydlidar //dev/rplidar udev symlinks). For a custom serial path, baudrate, or the LiDAR-over-WiFi-UDP bridge, use the Laser driver card on the Sensors tab instead of going through Bringup.

Bringup health check (is the robot really publishing?)

A running bringup process proves nothing on its own -- the microcontroller can be unplugged, the micro-ROS agent can have no session, the LiDAR can be on the wrong port. This probes the ROS graph itself: the publish rate on /odom/unfiltered (wheel odometry straight off the MCU), /odom (EKF-fused), /imu/data and /scan, plus the odom → base_footprint → laser TF chain that SLAM and Nav2 need before they will do anything useful.

Gamepad teleop

Virtual gamepad

Drive the robot from this page -- no physical joystick, and no terminal for teleop_twist_keyboard. Drag the stick (or use the arrow keys / WASD while it has focus) and Console publishes /cmd_vel at 20 Hz. Pair it with the Teleop RViz view to watch the robot move, which on a bare module running USE_FAKE_WHEEL firmware is the whole robot: cmd_vel drives the simulated wheels and the odometry comes back.

Deadman built in -- the robot is commanded to zero if this page stops sending for half a second, so closing the tab or losing Wi-Fi stops the robot instead of leaving it driving on the last command.

Visualize (RViz via browser)

Most robot computers are headless -- RViz has nowhere to open a window on. This runs RViz against a virtual display and serves it over noVNC, the same idea as the kasmvnc service in the console's docker/docker-compose.yaml, but native (no Docker) to match how the rest of Console installs things. Works whether you're viewing from the robot computer itself or a separate laptop on the network.

Heavier than the rest of Console -- RViz is a full Qt/OpenGL app, and on a small SBC (limited CPU, 4GB RAM class) running it headlessly through Xvfb adds real CPU/memory load on top of Bringup/Nav2. On constrained hardware, prefer the plain Sensors tab's /scan canvas viewer (much cheaper) and only reach for this when you actually need the full map/costmap/TF view.

The Teleop view is the one to use with a bare module running USE_FAKE_WHEEL firmware: the fixed frame is odom, so the robot is seen driving away from where it started, with odometry arrows tracing the path it thinks it took. Bare rviz2 opens with nothing configured and will look empty while you drive.

        micro-ROS agent -- the LiDAR talks to the robot computer directly (USB serial or its
        own WiFi-UDP relay), not through the MCU/agent link.
    
      
    
        
      
    

      
    
        
      
    

      
    
        
        
      
    
      
      
    Stored as /dev/serial/by-path/… (the physical USB port),
        which survives reboot and replug — unlike /dev/ttyUSBn, and
        unlike by-id, which many generic CP2102/CH340 lidar bridges can't populate.
        Most lidars share a generic UART chip, so pick by physical port; re-run
        detect after replugging to see which entry moved.

            point at this robot computer). Console bridges them into a local persistent serial
            device with socat, then points the driver at that device -- there's no
            other consumer for this feed today.

    Linux Rootless Container Guide
    
          
    Prevent root file ownership on bind-mounted directories
    
        
    
      
    
      
    
    

    
    
      
    💡 Why Rootless Docker on Linux?
    
      
    
        When standard (rootful) Docker executes container builds with volume mounts (-v "$(pwd):/workspace"), all generated files (such as .env, devices.generated.yaml, and build artifacts) are written as root:root. This causes local Git commit errors and permission denies during local development.
        Rootless Docker and Podman run completely inside your user namespace, guaranteeing all files stay owned by your normal user account.
      
    
    
    

    
    
      
    
        ⚡ 1-Click Setup: Ubuntu / Debian / Raspberry Pi OS
        
      
    
      
    # 1. Install prerequisites
sudo apt-get update && sudo apt-get install -y uidmap dbus-user-session slirp4netns
# 2. Run official rootless installer (non-root)
dockerd-rootless-setuptool.sh install
# 3. Enable user systemd service and persistent lingering
systemctl --user enable --now docker.service
loginctl enable-linger $USER
# 4. Point DOCKER_HOST to your user socket
export DOCKER_HOST="unix://${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/docker.sock"
grep -q "DOCKER_HOST" ~/.bashrc || echo 'export DOCKER_HOST="unix://${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/docker.sock"' >> ~/.bashrc
    
    
    

    
    
      
    
        🦭 Alternative: Podman (Rootless by Default — No Daemon!)
        
      
    
      
    sudo apt-get install -y podman  # Fedora: sudo dnf install -y podman
# Podman works immediately with zero daemon configuration:
podman run --rm hello-world
    
    
    

    
    
      🖥️ Windows & macOS Note
      
    
        On Windows (WSL2 / Docker Desktop) and macOS (Docker Desktop / Colima), volume mount permissions are already automatically mapped to the host user by the hypervisor layer. No rootless daemon configuration is required.
